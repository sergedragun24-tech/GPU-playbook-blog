# GPU Article Playbook

Система написания и редактуры технических статей про AI- и GPU-инфраструктуру для блога облачного провайдера. Работает как проект в Claude: инструкции проекта, промпты, пайплайн с тремя ветками, протокол сложной редактуры и глоссарий.

Автор: Сергей Драгун, технический редактор. Редакция системы на 12.10.2026.

Парный репозиторий [LLM-playbook-blog](https://github.com/sergedragun24-tech/LLM-playbook-blog) решает другую задачу: приёмку и фактчек готового черновика. Эта система пишет статью с нуля, правит чужой текст по замечаниям и сравнивает версии.

## Состав

```
instructions.md                 инструкции проекта: роль, файлы правил, пять правил, действующих всегда
prompts/
  tech-prompts.md               четыре промпта (1A/2A — статья с нуля, 1B/2B — редактура черновика) и общие блоки
  base-prompts.md               первая версия: два промпта из описания проекта
pipeline/
  edit-pipeline.md              общее ядро и ветки A (с нуля), B (редактура), C (сравнение версий)
  complex-edit-protocol.md      протокол для редактуры с несколькими версиями и внешними источниками
glossary.md                     решения по терминам со статусами «принято», «предложено», «спорно»
```

## Как устроено

Статья с нуля идёт в два промпта. PROMPT_1A проверяет SEO-ТЗ как инженер, фиксирует обязательные слои стека, собирает чек-лист ошибок под тему и список фактов, которые надо проверить на актуальность. PROMPT_2A пишет статью строго по этим параметрам и заканчивает её FAQ и блоком «Источники». Отдельно от статьи он выдаёт список технических допущений, которые надо проверить перед публикацией.

Редактура черновика тоже идёт в два шага. PROMPT_1B читает текст целиком без правок и фиксирует эталон стиля, покрытие слоёв стека и базовую терминологию. PROMPT_2B правит по одному блоку: замечания инженера, замечания редактора, новая версия блока, согласование, следующий блок.

Глубину статьи задают слои стека: приложение, MLOps, инфраструктура, железо. Любая статья про AI/GPU обязана вскрыть минимум два смежных слоя. На каждый ключевой тезис нужен технический якорь: механизм, метрика или ограничение.

Пайплайн добавляет к промптам обязательные проверки. Проверка рамки сверяет вопрос заголовка со сценарием, который описывают замеры и примеры. Чек-лист фактуры собирает таблицу «Утверждение | Источник | Вердикт» до черновика. Чек-лист MLOps ловит типовые технические ошибки. Литературный проход идёт отдельно от технического. Все правки сводятся в одну таблицу, пользователь отвечает по номерам, правки вносятся скриптом, который проверяет, что каждая замена нашла ровно одно совпадение.

## Система учится на статьях

После приёмки каждой статьи пополняются два файла. В глоссарий попадают термины, по которым принималось решение, со ссылкой на статью-источник. В чек-лист MLOps попадают новые типовые ошибки: например, после статьи про KV-кеш добавились правила о единицах памяти (ГиБ и ГБ), о независимости формата весов и формата кеша и о проверке страны происхождения оборудования.

Пять правил действуют всегда, в любом режиме: правка, на которую дано согласие, вносится в файл в том же ответе; утверждения о содержимом источника делаются только после повторного чтения; при нескольких версиях статьи каждая правка называет свой файл; удаление фрагмента сопровождается проверкой осиротевших ссылок; превышение объёма больше чем на 20% сообщается сразу.

## Что не вошло

Продуктовая справка компании, блок позиционирования с сильными сторонами продукта, раздел глоссария с названиями продуктов, тексты статей, журналы решений по статьям и разборы источников. Навык регистра `corporate-tech-register`, на который ссылаются инструкции, хранится на уровне аккаунта Claude.
