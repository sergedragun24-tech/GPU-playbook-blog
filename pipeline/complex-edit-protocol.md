# PROMPT_COMPLEX_EDIT — протокол сложной многодокументной редактуры

Компаньон к `prompts/tech-prompts.md`. Использует его общие блоки
(`POSITIONING`, `RBC_STYLE`, `TERMINOLOGY_RUSSIFICATION`, `FACT_FRESHNESS_CHECK`,
`SOURCES_BLOCK`, `TECH_ASSUMPTIONS_BLOCK`) без изменений — они относятся к
качеству текста и применяются одинаково в любом сценарии.

Этот протокол — не про стиль. Он про то, как не терять контроль над задачей,
когда редактура выходит за рамки "один черновик → один проход правок":
несколько версий черновика, факты из внешних источников, риск разъехавшихся
версий файла, риск осиротевших ссылок после удаления кусков текста.

## Когда применять

Признаки, что задача — не для линейного `PROMPT_1B/2B`, а для этого протокола:

- Есть больше одного документа-источника (несколько вкладок черновика,
  разные версии, разные форматы — .odt/.docx/.md), и их нужно сверять
  между собой, а не читать один раз последовательно
- Часть фактуры в статье опирается на внешние исследования, которые нужно
  проверять поиском, а не брать из документов пользователя
- В процессе работы создаются параллельные версии итогового текста
  (сравнение структур, A/B вариантов)
- Правки идут не блоками сверху вниз, а вразнобой — то откат, то возврат,
  то сверка "а это точно оттуда"

Если ничего из этого нет — используйте обычный `PROMPT_1B` (аудит) →
`PROMPT_2B` (правка по блокам). Не усложняйте линейную задачу этим
протоколом без необходимости.

## EXECUTION_DISCIPLINE — обязательные правила выполнения

Эти правила жёстче, чем в обычной редактуре, потому что цена ошибки —
не стилистическая шероховатость, а расхождение между тем, что сказано
в диалоге, и тем, что реально в файле.

```
NO_PROMISE_WITHOUT_ACTION:
  Любое согласие с правкой в диалоге ("уберу X", "заменю Y на Z",
  "добавлю ссылку") ОБЯЗАНО сопровождаться реальным вызовом инструмента
  правки файла В ЭТОМ ЖЕ ОТВЕТЕ.
  Запрещено: подтвердить правку словами и оставить её только в тексте
  ответа, полагая, что пользователь перенесёт её сам, если только
  пользователь явно не попросил "покажи текстом, я сам вставлю" —
  и даже в этом случае, если существует мастер-файл, его тоже нужно
  обновить, если не сказано обратное.

NO_MEMORY_CLAIMS_ABOUT_SOURCES:
  Утверждения вида "этого нет в черновике", "это я сам добавил",
  "в документе X написано Y" — ЗАПРЕЩЕНО делать по памяти о более
  раннем прочтении. Каждое такое утверждение требует повторного
  просмотра актуального текста источника в ЭТОМ ЖЕ ходе, если с момента
  последнего чтения прошло больше нескольких реплик или если это
  утверждение станет основанием для правки/удаления контента.
  Если проверка невозможна (источник недоступен) — утверждение
  формулируется с explicit hedge: "по памяти о более раннем прочтении,
  не перепроверено сейчас" — не как факт.

SINGLE_SOURCE_OF_TRUTH:
  Если существует более одного файла с версией статьи (например,
  вариант для сравнения структуры) — в начале работы явно зафиксировать,
  какой файл считается рабочим. При любой правке — называть, в какой
  файл она вносится, если это не единственный существующий файл.
  Переключение "рабочего" файла происходит только по явному указанию
  пользователя, никогда по умолчанию или по предположению.

ORPHAN_CHECK_ON_DELETE:
  При удалении любого раздела, абзаца или тезиса — обязательная проверка
  в ЭТОМ ЖЕ ходе:
    - остались ли в списке источников записи, которые подтверждали
      только удалённый фрагмент и теперь ничего не подтверждают
    - остались ли в FAQ вопросы/ответы, ссылающиеся на удалённый факт
      или кейс
    - остались ли в других разделах статьи (включая заключение) фразы,
      которые ссылались на удалённый фрагмент ("как говорилось выше",
      конкретные названия/цифры из удалённого куска)
  Найденные сироты — чинить сразу же, не дожидаясь, когда пользователь
  их заметит и спросит.

LENGTH_BUDGET_ALERT:
  Если задан целевой объём (в знаках), и текущая версия превышает его
  более чем на 20% — сообщить об этом явно в том же ответе, где правка
  довела текст до превышения, не дожидаясь отдельного вопроса
  пользователя об объёме. Предложить, что конкретно можно сократить.
```

## MULTI_DOCUMENT_RECONCILIATION — сверка нескольких источников

```
Когда на входе несколько версий/вкладок черновика:

1. Перед тем как утверждать что-либо о происхождении контента —
   прочитать ВСЕ версии целиком, не по фрагментам и не по памяти
   о более раннем эпизоде диалога. Частичное чтение — частая причина
   ошибочных атрибуций.

2. При сверке "что взято из документа X" — использовать построчное
   сравнение (например, поиск точных фраз, а не пересказ по памяти),
   и явно показывать пользователю, что именно совпало, а не только вывод.

3. Если у двух версий-вкладок одинаковое или почти одинаковое название —
   явно проверить, идёт ли речь об одном и том же файле, прежде чем
   делать выводы о процентном соотношении или содержании. Название
   не гарантирует идентичность контента.

4. Процентные или количественные оценки происхождения контента
   ("N% статьи взято из документа Y") — только на основе фактического
   подсчёта (посчитать длину пересекающихся фрагментов через код),
   а не на глаз. Показывать пользователю, как считали, а не только число.
```

## VERSION_LOG — учёт параллельных версий

```
Если в ходе работы создаётся более одной версии итогового текста
(например, для сравнения структурных решений):

  - каждая версия получает явное, разное имя файла
  - при создании второй версии — явно сказать, что первая версия
    не изменена и остаётся доступной для сравнения
  - при любой последующей правке — прежде чем вносить её, уточнить
    (если не очевидно из контекста), в какую версию она идёт
  - если пользователь работает над своей копией одной из версий вручную
    (правит в .odt/.docx у себя) — явно спросить или зафиксировать,
    какая версия сейчас "боевая", и дальнейшие правки от Claude вносить
    именно в неё, а не в ту, что осталась неизменной с более раннего
    этапа работы
```

## Формат ответа при работе по этому протоколу

При каждой правке в рамках этого протокола ответ должен явно содержать:

1. **В какой файл вносится правка** (если файлов несколько)
2. **Что именно меняется** — с указанием, что было и что стало
3. **Проверка на сирот** — если правка была удалением, явно сказать
   "проверил источники/FAQ на осиротевшие ссылки — [нашёл / не нашёл]"
4. Если объём превышен — явное упоминание этого без ожидания вопроса

Не нужно превращать это в бюрократический чек-лист на каждую мелкую
правку — но для структурных изменений (удаление раздела, слияние
разделов, смена рабочей версии) эти четыре пункта обязательны.
