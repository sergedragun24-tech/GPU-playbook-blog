# Промпты для технических статей — AI / GPU / обучение моделей

Основа: адаптация корпоративных SEO-промптов (v2) под технические статьи с усиленным инженерным контролем.
Два сценария, каждый в два этапа:

- **Вариант A — статья с нуля** (по теме/SEO-ТЗ): `PROMPT_1A` → `PROMPT_2A`
- **Вариант B — редактура черновика**: `PROMPT_1B` → `PROMPT_2B`

Общие блоки (позиционирование, стиль, глубина по слоям стека, адаптивный чек-лист, проверка актуальности фактов) вынесены отдельно и используются во всех четырёх промптах — чтобы термины и решения были едиными между сценариями.

## ОБЩИЕ БЛОКИ (используются во всех промптах)

### POSITIONING — позиционирование компании для AI-тематики

Заполняется под конкретного провайдера. В рабочей версии здесь перечислены
сильные стороны продуктовой линейки, из которых редактор выбирает релевантные теме.

```
PRODUCT_POSITIONING:
  value_proposition: "[Компания] — облачный провайдер с собственной GPU-инфраструктурой"
  tone: technological
  strengths_candidates:
    # открытый список — редактор выбирает релевантные под конкретную тему,
    # не нужно вставлять все сразу
    - "[сильная сторона продукта, подтверждённая продуктовой справкой]"
  constraints:
    - "не упоминать конкурентов по имени"
    - "не давать неподтверждённые цифры SLA/производительности/цен на GPU-часы"
    - "не формулировать юридические выводы без явной фактуры (152-ФЗ, экспортный контроль и т.п.)"
    - "не выдавать характеристики конкретных GPU/моделей без проверки актуальности (см. FACT_FRESHNESS_CHECK)"
  segment_hint: "enterprise / upper mid-market, ИТ-директора, ML-инженеры, архитекторы инфраструктуры, DevOps/MLOps"
```

### ГЛУБИНА ПО СЛОЯМ СТЕКА (вместо уровня аудитории)

Идея: глубина статьи определяется не тем, "для новичка или эксперта", а тем, **какие слои системы обязаны быть вскрыты**. Материал не имеет права остаться описательным ("GPU ускоряет обучение моделей") там, где тема требует механики. Слой не задаёт стиль изложения — стиль остаётся разговорным и понятным, но за каждым утверждением должен стоять конкретный механизм этого слоя.

```
ARCHITECTURE_LAYERS:
  - application_layer:
      описание: "API инференса, SDK, промпт-инжиниринг, интеграция в продукт"
      маркер_поверхностности: "статья говорит 'модель отвечает на запросы' без упоминания
        батчинга, контекстного окна, latency vs throughput"
  - mlops_layer:
      описание: "оркестрация обучения/инференса, версионирование моделей, RAG-пайплайны,
        fine-tuning workflows, автоскейлинг инференс-сервисов"
      маркер_поверхностности: "'модель дообучается на данных компании' без упоминания
        LoRA/full fine-tuning/RAG как разных путей и разных требований к данным"
  - infrastructure_layer:
      описание: "кластеризация GPU-узлов, шардинг, изоляция тенантов (vGPU/MIG/MPS,
        включая различие MIG vs MIG-backed vGPU и лицензирование NVIDIA vGPU),
        сетевая топология (NVLink, InfiniBand, RoCE), хранение checkpoint'ов"
      маркер_поверхностности: "'GPU выделяются по требованию' без объяснения, что стоит
        за multi-instance изоляцией и как это влияет на задержку у соседних тенантов"
      для_инфраструктурных_статей_обязательно:
        - "тип и топология интерконнекта (InfiniBand/RoCE) — не просто упоминание,
          а объяснение, на что именно это влияет (all-reduce при распределённом обучении,
          масштабирование на большое число узлов)"
        - "тип охлаждения (воздушное vs жидкостное/DLC) — как фактор плотности размещения
          GPU-узлов и, как следствие, TCO дата-центра"
        - "лицензирование NVIDIA vGPU как отдельная статья расходов при выборе схемы
          разделения GPU (MIG без vGPU vs MIG-backed vGPU)"
  - hardware_layer:
      описание: "архитектура GPU (потоковые мультипроцессоры, объём видеопамяти,
        пропускная способность памяти), точность вычислений (FP8/FP16/INT8),
        пропускная способность интерконнекта, охлаждение/энергопотребление
        на уровне, значимом для инфраструктурных решений и расчёта TCO"
      маркер_поверхностности: "GPU называются взаимозаменяемыми без разницы в объёме
        видеопамяти, пропускной способности памяти и поддерживаемой точности вычислений"

TCO_FACTORS_FOR_INFRA_ARTICLES:
  # обязательный список факторов, которые нельзя опускать в статьях про GPU-инфраструктуру,
  # если статья претендует на роль материала про совокупную стоимость владения
  - "стоимость лицензирования NVIDIA vGPU при MIG-backed vGPU (в отличие от MIG без
    vGPU-слоя, где лицензии не требуется)"
  - "тип и пропускная способность интерконнекта (InfiniBand/RoCE) — влияет на время
    обучения при распределённых нагрузках, а значит и на итоговую стоимость GPU-часов"
  - "тип охлаждения (воздушное vs жидкостное) — влияет на плотность размещения
    GPU-узлов на площадку и на энергопотребление, а значит на стоимость эксплуатации"
  - "простои и утилизация GPU-парка — GPU-час без учёта простоя занижает
    реальную стоимость владения"
  - "стоимость хранения checkpoint'ов и данных для обучения/RAG — часто опускается
    при сравнении по цене GPU-инстанса"

REQUIRED_LAYERS_PER_TOPIC:
  # фиксируется на Этапе 1 каждого промпта, индивидуально под тему.
  # Правило: минимум 2 смежных слоя обязательны для любой статьи из домена AI/GPU.
  # Если тема по формулировке кажется чисто application_layer (например,
  # "как использовать API инференса") — всё равно должен быть явный переход
  # хотя бы к mlops_layer (что стоит за запросом: батчинг, очереди, autoscaling),
  # иначе статья скатывается в маркетинговый пересказ документации.

DEPTH_ANCHOR_RULE:
  # на каждый ключевой тезис — один технический якорь: механизм, метрика или ограничение,
  # который нельзя убрать без потери смысла тезиса.
  пример_плохо: "vGPU обеспечивает гибкое разделение GPU между пользователями"
  пример_хорошо: "vGPU делит GPU на виртуальные профили на уровне драйвера — в отличие
    от MIG, где разделение происходит на уровне аппаратных инстансов, поэтому у vGPU
    ниже изоляция по производительности между тенантами при пиковой нагрузке"
```

### АДАПТИВНЫЙ ЧЕК-ЛИСТ ОШИБОК (AI/GPU-домен)

В отличие от фиксированной таблицы (distributed systems), для AI/GPU-тематики ошибки сильно зависят от конкретной темы статьи. Поэтому чек-лист — не готовая таблица, а **инструкция по генерации чек-листа под тему** на Этапе 1 каждого промпта.

```
ADAPTIVE_CHECKLIST_INSTRUCTION:
  При аудите (ТЗ или черновика) — сформировать чек-лист типовых ошибок именно под тему,
  используя следующие категории как затравку (не как исчерпывающий список):

  - throughput vs latency:
      "обработали больше запросов" и "быстрее ответили" — разные и часто конфликтующие
      оптимизационные цели; смешение ведёт к завышенным обещаниям
  - GPU-часы vs TCO:
      стоимость GPU-часа не равна полной стоимости владения — простои, оркестрация,
      сеть, хранение checkpoint'ов остаются за кадром
  - MIG vs vGPU vs MPS:
      разные механизмы разделения GPU (аппаратное партиционирование vs виртуализация
      на уровне драйвера vs software time-slicing) — нельзя ставить в один ряд
      как взаимозаменяемые
  - MIG-backed vGPU и лицензирование:
      MIG-backed vGPU — это vGPU поверх MIG-инстансов, а не поверх целого физического GPU;
      частая ошибка — не различать "просто MIG" (нужна поддержка на уровне ОС/контейнеров,
      лицензия NVIDIA vGPU не требуется) и "vGPU/MIG-backed vGPU" (требует лицензии
      NVIDIA vGPU — это отдельная статья расходов и коммерческий фактор, который нельзя
      опускать при сравнении схем разделения GPU по TCO
  - InfiniBand и типы охлаждения как факторы TCO:
      скорость и топология интерконнекта (InfiniBand/RoCE) и тип охлаждения
      (воздушное vs жидкостное/DLC) — не второстепенные детали "железа", а прямые
      факторы TCO и производительности распределённого обучения; нельзя описывать
      кластер без них, если статья претендует на инфраструктурный слой
  - quantization vs fine-tuning vs full training:
      квантование меняет представление весов для инференса, дообучение меняет веса
      под задачу, обучение с нуля — принципиально другой по стоимости процесс;
      смешение этих терминов — частая ошибка в маркетинговых текстах
  - RAG vs fine-tuning:
      разные подходы к "обучению модели знаниям компании" с разными требованиями
      к данным, инфраструктуре и рискам (утечка контекста vs утечка весов)
  - context window vs память модели:
      увеличение контекстного окна не эквивалентно "модель запоминает больше" —
      это разные механизмы (attention над контекстом vs параметры весов)
  - VRAM vs bandwidth:
      объём видеопамяти не определяет производительность инференса сам по себе —
      без учёта пропускной способности памяти утверждение неполное
  - инференс batch-размер vs интерактивность:
      увеличение батча повышает throughput, но повышает latency для отдельного
      запроса — нельзя утверждать оптимизацию по обоим параметрам одновременно
      без оговорки о trade-off
  - автоскейлинг GPU-пулов:
      "автоскейлинг решает проблему нагрузки" — универсальное утверждение;
      GPU-инстансы поднимаются медленнее CPU из-за загрузки весов/драйверов,
      это ограничивает применимость автоскейлинга для real-time сценариев
  - мультитенантность и изоляция:
      "GPU можно безопасно шарить между клиентами" без уточнения механизма
      изоляции — потенциально вводящее в заблуждение утверждение, особенно
      в контексте 152-ФЗ/регулируемых данных
  - устаревание конкретики:
      конкретные модели GPU, версии моделей LLM, цены — самая быстро стареющая
      часть текста; требует FACT_FRESHNESS_CHECK (см. ниже)

  Формат вывода чек-листа на Этапе 1: таблица "Паттерн ошибки — Пример из ТЗ/черновика —
  Как исправить", сгенерированная под конкретную тему, а не скопированная из этой затравки.
```

### FACT_FRESHNESS_CHECK — проверка актуальности фактуры

```
FACT_FRESHNESS_CHECK:
  Обязателен для любого упоминания:
    - конкретных моделей GPU и их характеристик (VRAM, bandwidth, precision support)
    - версий и context window LLM (проприетарных и open-source)
    - версий инференс-фреймворков и оркестраторов (vLLM, TensorRT-LLM, Kubernetes
      GPU operator, Slurm и т.п.)
    - цен на GPU-часы / инстансы (любых, включая индикативные)
  Правило:
    - если у модели есть доступ к поиску — использовать его для проверки перед
      фиксацией цифры/версии в тексте
    - если доступа нет — не изобретать цифру; помечать утверждение в
      TECH_ASSUMPTIONS_BLOCK как "требует проверки на дату публикации"
    - рядом с проверенной цифрой — короткая пометка источника периода
      ("на момент публикации", без точных дат, если дата не проверена явно)
```

### TERMINOLOGY_RUSSIFICATION — глоссарий русификации терминов

По умолчанию термины домена AI/GPU русифицируются, если у термина есть устоявшийся
русскоязычный эквивалент, понятный целевой аудитории (ML-инженеры, DevOps, ИТ-директора).
Англицизм оставляется без перевода только если русский эквивалент реально не используется
в профессиональной среде или создаёт двусмысленность — такие исключения перечислены ниже.

```
GLOSSARY_DEFAULT:
  latency                → задержка
  throughput             → пропускная способность
  fine-tuning            → дообучение
  full fine-tuning        → полное дообучение
  training                → обучение
  inference               → инференс (устоявшийся термин, не переводится; при первом
                             появлении дать пояснение: "инференс — генерация ответа
                             уже обученной моделью, в отличие от обучения")
  batch                    → батч (устоявшийся, не переводится) / при необходимости
                             "пакет запросов" для нетехнического контекста
  batch size               → размер батча
  checkpoint                → контрольная точка (при первом упоминании — с пояснением;
                              далее допустимо "чекпоинт", если так короче и не мешает
                              единообразию)
  autoscaling              → автомасштабирование / автоскейлинг — зафиксировать один
                              вариант в TERMINOLOGY_BASELINE на статью и использовать
                              единообразно
  multi-tenancy            → мультиарендность / мультитенантность — зафиксировать один
                              вариант на статью
  quantization             → квантование
  context window            → контекстное окно
  bandwidth (memory)        → пропускная способность памяти
  interconnect               → интерконнект (устоявшийся) / "сетевое соединение между
                                узлами" при первом упоминании
  cooling (DLC)               → жидкостное охлаждение / прямое жидкостное охлаждение
  precision (FP8/FP16/INT8)    → точность вычислений
  licensing                     → лицензирование

GLOSSARY_KEEP_AS_IS:
  # термины, где английский вариант устоялся сильнее русского эквивалента
  # и перевод создаёт путаницу — не русифицировать принудительно
  - "GPU" (не "видеокарта" — не тот регистр для B2B-инфраструктурной статьи)
  - "vGPU", "MIG", "MPS" — названия конкретных технологий NVIDIA, не переводятся
  - "RAG" — устоявшаяся аббревиатура, при первом упоминании дать расшифровку
    и краткое пояснение по-русски
  - "LoRA" — название метода, не переводится

ПРАВИЛО ПРИМЕНЕНИЯ:
  - при первом появлении термина из GLOSSARY_DEFAULT — используется русский эквивалент,
    без англицизма в скобках, если эквивалент однозначен (например, latency → задержка,
    без "(latency)" рядом)
  - если термин неоднозначен без английского оригинала (например, "автомасштабирование"
    можно спутать с масштабированием инфраструктуры вообще) — при первом появлении
    в скобках указать англицизм один раз: "автомасштабирование (autoscaling)", далее
    по тексту — только русский вариант
  - выбранный вариант фиксируется в TERMINOLOGY_BASELINE (вариант B) или в
    ADAPTIVE_CHECKLIST/EDITOR_NOTES (вариант A) и применяется единообразно
    по всей статье
```

### SOURCES_BLOCK — обязательный блок источников в конце документа

```
Правило действует для ОБОИХ сценариев (с нуля и по черновику):
  - любой финальный документ (готовая статья целиком, включая случай, когда
    статья собрана из отдельно отредактированных блоков по варианту B)
    обязан заканчиваться блоком "Источники"
  - формат: нумерованный список; для внешних публичных источников — прямая
    ссылка; для внутренних/проектных документов без публичной ссылки —
    название документа как оно есть
  - в блок попадают все источники, на данные которых опирается текст:
    цифры, статистика, кейсы, цитаты, названия исследований
  - блок источников не сокращается и не пересказывается — это ссылочный
    список, а не резюме
  - для варианта B: блок источников формируется на финальной сборке всех
    согласованных блоков в один документ, не на уровне отдельного блока
```

## STYLE_RULES (используются во всех промптах)

```
Тон и подача:
  - разговорный, но технически точный — без пафоса и без упрощений
  - каждая мысль — отдельное предложение, не нанизывать причастные обороты
  - «Дело в том, что…», «Вдобавок…», «По мере того как…» — допустимые связки
  - короткий ударный абзац в конце раздела лучше длинного резюме
  - избегать «не просто X, а ещё и Y» — ложный контраст

Технические правила:
  - универсальные утверждения требуют оговорок: «в большинстве архитектур»,
    «для inference-нагрузок», «при корректной настройке автоскейлинга»
  - не смешивать разные типы решений/механизмов в одном утверждении без уточнения
  - при первом упоминании термина — короткое пояснение в том же предложении
  - инструменты/механизмы разного класса не ставить в один ряд без пояснения различий
  - при первом появлении англицизма — зафиксировать русский эквивалент,
    применять единообразно по всей статье (пополняет TERMINOLOGY_BASELINE);
    по умолчанию использовать GLOSSARY_DEFAULT (см. блок TERMINOLOGY_RUSSIFICATION) —
    latency → задержка, fine-tuning → дообучение, throughput → пропускная способность
    и т.д.; не русифицировать принудительно только термины из GLOSSARY_KEEP_AS_IS
    (GPU, vGPU, MIG, MPS, RAG, LoRA)
  - кальки с английского заменять на русские эквиваленты
    («в продуктовой среде» → «в рабочей среде», «датацентровый» → «для дата-центров»)

Структура текста:
  - разбивать плотные абзацы: проблема и решение читаются отдельно
  - визуальные якоря (выделение термина) — когда в блоке 3+ элемента
  - таблицы не дублируют текст: либо колонка из таблицы, либо перечисление из текста
  - заголовок блока соответствует содержанию

Что не делать:
  - маркетинговые формулировки («революционная технология», «на острие AI»)
  - академический тон
  - low-level детали без необходимости, если тема их не требует по REQUIRED_LAYERS
  - подавать одно решение как универсальный стандарт для всех сред
```

### RBC_STYLE — литературный регистр (деловой стиль РБК Компании)

Эти правила уточняют и дополняют общий STYLE_RULES выше конкретными приемами,
отработанными на практике. При конфликте с общими формулировками выше —
приоритет у этого блока, он более конкретный.

```
Вход в текст:
  - интро строится через контекст/тренд («последние два-три года…»,
    «за последний год…»), а не через хлесткую декларацию-клише
    («X перестал быть экспериментом», «X больше не роскошь»)
  - не начинать статью с готового вывода — сначала контекст, потом то,
    что читатель узнает («разбираемся, почему…», «разбираемся, что стоит
    за этим трендом»)
  - избегать резких/разговорных метафор в первом абзаце («человек с
    закрытыми глазами», «сидит с открытым счетчиком») — метафоры уместны
    точечно и дальше по тексту, не в первых трех предложениях

Длина и структура предложения:
  - не больше одной сложноподчиненной конструкции на предложение;
    если внутри уже есть «который/потому что/хотя» — второй такой же
    оборот в это же предложение не добавлять, выносить в отдельное
  - длинную конструкцию с перечислением через запятые внутри одного
    предложения (3+ элемента) дробить на два предложения
  - не открывать два предложения подряд в одном абзаце словом «это» —
    искать другой субъект («такой подход», «такой пробел», «эта функция»)
  - минимизировать тире: там, где тире используется для перечисления
    или вложенного пояснения (не как «X — это Y»), почти всегда яснее
    заменить на точку, запятую или двоеточие

Раскрытие тезиса:
  - тезис не оставлять голым: сразу за ним — объяснение «почему это так»
    или «что это значит на практике», а не переход к следующему тезису
  - термин или метрика поясняются в момент первого появления, а не
    предполагается, что читатель их знает («EBIT» → сразу расшифровка
    в скобках; «рекурсивные затраты» → сразу в чем механизм)
  - для абстрактных величин, которые ничего не говорят неподготовленному
    читателю (конкретная валюта, отраслевой жаргон) — давать бытовую
    аналогию или относительную величину («на порядок дороже» вместо
    «центы и доллары», если аудитория не привязана к этой валюте)

Источник vs вывод:
  - если предложение начинается «по данным X» или «согласно отчету Y» —
    в этом же предложении не должно быть добавленной от себя интерпретации;
    вывод или экстраполяция — это отдельное предложение с явной пометкой
    («это значит, что…», «на практике это означает…»), а не слияние с фактом
  - при описании кейса/примера из отчета — сначала точно то, что в отчете
    есть (цифры, механика, кто/что), потом отдельно — более широкий вывод
    или связь с другой темой; не выдавать общий вывод за часть источника

Термины и роли:
  - если в тексте фигурирует конкретная техническая роль (провайдер,
    вендор, оператор, разработчик модели) — использовать один термин
    последовательно по всей статье, кроме случаев, когда термин —
    официальное название роли в конкретном регуляторном документе
    (тогда термин из документа сохраняется как есть в этом фрагменте,
    остальной текст использует общий термин)
```

## Открытые моменты для калибровки

- Конкретный набор `strengths_candidates` в POSITIONING стоит расширять по мере появления новых фактов о продуктовой линейке (GPU-инстансы, managed MLOps, партнёрства) — сейчас список кандидатов, не финальный.
- `REQUIRED_LAYERS_PER_TOPIC` определяется вручную на Этапе 1 каждого промпта — можно позже формализовать в виде таблицы "тип темы → обязательные слои", если наберётся достаточно прецедентов.
- Стоит решить, нужен ли отдельный режим для статей, где сравнение GPU/моделей — единственный контент (например, "H100 vs H200 vs B200") — там FACT_FRESHNESS_CHECK становится не вспомогательным, а центральным элементом промпта.
